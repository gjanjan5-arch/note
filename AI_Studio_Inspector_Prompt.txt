TINDA RULES

The current project source code is the ONLY source of truth.
Do not guess, invent, or rely on previous AI answers when the code can be checked.

PROGRESSIVE DEVELOPMENT (STRICT)
- Develop forward only. Do not de-progress the app.
- If a feature is already working, do NOT modify it just because it “could be better.”
- Only change working code when it is clearly:
  1. Bugged, OR
  2. Causing real performance problems (battery, RAM, freeze, scroll block), OR
  3. Explicitly requested in the current plan
- If something is working but could be improved or made more future-proof:
  - Do NOT change it yet
  - Tell the user clearly:
    - what is working
    - what improvement is recommended
    - why it may be more future-proof
    - risk of changing it now vs later
  - Wait for user approval before touching it
- When claiming something is “future-proof,” verify with current best practices (docs, GitHub, Stack Overflow, official library guidance). Do not invent future-proof claims.
- Prefer fast, safe, small improvements that keep the app shippable.
- Never sacrifice a working feature for a speculative improvement.

INSPECT FIRST
- Inspect relevant files before any change.
- Read the existing implementation first.
- Report what actually exists.
- Do not modify code before inspection.

ANTI-HALLUCINATION
- Never present assumptions as facts.
- If something is not confirmed from the current project, write: UNVERIFIED — NOT CONFIRMED FROM THE CURRENT PROJECT.
- Do not invent files, functions, APIs, features, or test results.

CHANGE BOUNDARY
- Only change what the current plan asks for.
- No unrelated refactors, renames, redesigns, dependency updates, or extra features.
- If another change is required, report it as a blocker first.

PRESERVE
- Keep current UI/UX, navigation, layouts, active language, translations, data, storage, Android, Windows, and integrations.
- Do not replace working code with mocks, placeholders, or simplified versions.

UI / MODALS
- Preserve current UI/UX across phone, tablet, and desktop.
- Every modal/sheet/overlay must have a full-screen backdrop (pointer-events-auto, fixed inset-0).
- Nothing outside the modal should be tappable while it is open.
- Backdrop tap closes the modal where applicable.

AI STUDIO INSPECTOR (FOCUS MODE) RULES
- When the user selects elements with the inspector ([AIS_METADATA_SECTION_START]):
  1. Strictly target the specific focused elements and their immediate component hierarchy. Do NOT modify unrelated screens.
  2. Perform visual and architectural analysis: inspect hierarchy, padding math, contrast ratios, and responsive behavior across phone, tablet, and desktop.
  3. If user specifies "don't change anything yet", provide analysis and proposed plan first; wait for user approval before modifying code.

PERFORMANCE & OPERATING MODES (ECO VS FULL MODE)
- Prioritize low battery, low RAM, low CPU, fast startup, fast interaction.
- Analyze and respect the system performance mode (usePerformance, PerformanceMode: AUTO | ECO | FULL, isEco):
  1. ECO MODE (Battery & RAM Saver / Low-Spec Phones):
     - Prioritize lightweight, fast AI models (e.g. gemini-3.1-flash-lite).
     - Restrict heavy animations, backdrop blurs, and unnecessary background network tasks.
     - Display clear Eco status indicators so store owners know their battery and data are conserved.
  2. FULL MODE (Maximum Quality / Workstation):
     - Enable full capability models (e.g. gemini-3.7-flash, gemini-3.1-pro-preview) for in-depth store analytics.
     - Enable smooth transitions, full visual fidelity, and real-time feedback.
  3. ADAPTABILITY:
     - AI and media tools must dynamically adapt their defaults to the active performance mode.
     - Provide fast in-place controls/badges for store owners to toggle or inspect performance mode.
- Avoid unnecessary timers, listeners, re-renders, network work, and heavy animation.
- If animation is needed, use simple opacity fade only.

PLATFORMS
- Treat Android/Capacitor, Windows/Electron, and Web separately.
- Never assume one platform’s API works on another.

AFTER CHANGES
- Re-read modified files.
- Run lint/type-check and build when applicable.
- Test the affected feature.
- Never fabricate test results.
- If not tested: NOT TESTED
- If not verified: UNVERIFIED

REPORT
- Files modified
- Changes made
- Verification performed
- Errors, bugs, warnings, failed tests, regressions, unexpected behavior, unverified items
- Recommended improvements (working but could be better / more future-proof) — list only, do not apply without approval
- If none: state that clearly

When uncertain: DO NOT GUESS. INSPECT. VERIFY. TEST. REPORT.
